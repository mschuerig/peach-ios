## Pattern instance 1 — Story 85.1 (post-merge fix loop)

The visible form: five "Fix story 85.1: …" commits over ~12 hours, each a refinement of the same architect framing (`muteForFade` as silencer; extend the audio-stop chain to cover more callers). Each patch added complexity to an existing serialization chain. None closed the symptom.

The verification listening test (Task V) was conceptually the same kind of move as Task 1 verification in the original spec — but the spec workflow's verification gate only covers *new* code changes, not *bug-chase reopenings*. The bug-chase mode has no equivalent gate, so the architect's framing flowed straight into patch #1.

## Pattern instance 2 — Story 85.6 (in-session, iOS 26 a11y-tree regression)

The spec was clean: Task 1 was an explicit evaluation of four candidate mechanisms (`swift-snapshot-testing`, `ViewInspector`, `XCUITest`, bespoke `accessibilityElements` inspection). Michael picked the bespoke approach.

Then in implementation, the chosen path didn't work on iOS 26. The Spec Change Log records the iteration:

> *"The first pass of PF-036 and PF-040 implemented runtime-hosted assertions (`UIHostingController` → `UIWindow.makeKeyAndVisible()` → walk `accessibilityElements`...). On iOS 26, SwiftUI's accessibility-tree materialization in `UIHostingController` unit-test contexts is broken — the hosted view's `accessibilityElements` is always `[]` **regardless of `makeKeyAndVisible()`, `UIWindow(windowScene:)`, `UIAccessibility.post(.screenChanged, …)`, runloop ticks, or live-window injection.** Confirmed by cashapp/AccessibilitySnapshot open issues #245 (June 2025) and #259 (September 2025); no supported workaround from Apple."*

Same shape as 85.1, smaller magnitude, no commits between attempts: **five different incantations of the same framing** ("runtime-hosted accessibility-tree introspection should work; I just need to invoke it right") before pivoting to a completely different approach (layout measurement of `categoryHeader(text:)`).

The cashapp/AccessibilitySnapshot GitHub issues that proved the path was broken were found *after* the pivot. A 5-minute search probe ("is `UIHostingController.accessibilityElements` known to be broken on iOS 26?") **before** the first incantation would have surfaced those issues and pre-empted the five tries.

This instance does not show up in the commit history because it was all squashed into the single implementation commit. It is only visible in the Spec Change Log.

## Pattern instance 3 — Story 85.8 (high review-patch density)

Different shape. The implementation lands in a single commit of **35 files, 1,932 lines changed**. Step-04 review applies **13 patches**. `/simplify-code` applies **9 more**. **4 PFs are deferred** to follow-up entries. That's 26 distinct review-driven changes within one session before commit.

Read in good light: this is the BMad workflow working — the adversarial review step is *supposed* to catch issues. The 13 patches are mostly real bugs, not noise.

Read in bad light: the initial implementation got 13 things wrong in a domain (audio-session lifecycle, AVAudioEngine configuration changes, media-services-lost recovery) where the project already had two memory entries warning about precisely this kind of complexity. An audit that produces such a long patch list suggests the initial implementation pass was working at too high a velocity for the domain.

I'm not calling this an anti-pattern in itself. I'm flagging that **iteration density that high inside one session is a signal worth a separate conversation**.

## Root causes — recap

(All five still hold; reorganized to reflect the broader sample.)

1. **No falsification-first rule in bug-chase mode or in-session iteration.** Story specs require a Task 1 verification gate before any code change. Post-merge bug-chase (85.1) and mid-implementation framing pivots (85.6) have no equivalent gate. The architect's framing in 85.1 and the runtime-a11y-tree framing in 85.6 both became patch #1 instead of test #1.

2. **Memory recall was aspirational, not mechanical.** Two relevant memory entries (`feedback_verify_architect_framing`, `reference_rt_audio_framing`) existed before Epic 85 and both captured the exact failure mode for 85.1. Neither fired at the moment that mattered.

3. **Additive bias under symptom pressure.** 85.1: every patch *adds* complexity to a chain; the actual fix is subtractive. 85.6: every incantation *adds* lifecycle ceremony to the runtime host; the actual fix abandons runtime hosting entirely.

4. **Research came last, not first.** 85.1: 102-agent deep-research pass *after* 4 failed patches. 85.6: cashapp GitHub issues found *after* 5 failed incantations. In both cases, a cheap probe ahead of the first patch would have surfaced the same evidence.

5. **No audio-path verification gate before declaring a story done.** All four schemes were green at 85.1's first commit; the bug was only audible. Visual-features rule exists; audio-features rule did not.

## What's changing — adopted measures

The retrospective went through a refinement step: Michael flagged that the **patch-count rule** is downstream of the actual problem. Counting commits catches *consequences* of the failure mode, not its *generator*. The generator is **uninterrogated assumptions + confusing motion with progress** — invisible while it's happening, because confidence stays high as evidence accumulates against it. The fix is **self-awareness in the process**, not a counter.

Four memory entries, layered from upstream to downstream. They take effect on the next Claude session.

### A (PRIMARY) — Progress-check + substantiation — `feedback_progress_check_and_substantiation.md`

> On the **first** failed attempt at a fix or implementation — symptom unchanged, test still failing, behaviour unaltered — pause before the next attempt and answer two questions, in writing:
>
> **Q1 — Am I really going forward?** What signal would have indicated progress? Did it appear, even partially? If not, why is the next attempt expected to produce one? *"I'll try a variant"* is not an answer.
>
> **Q2 — Can I substantiate this claim?** What premise am I acting on? Where did it come from? Is it verified or assumed? What evidence would I cite to a skeptic?

**Why first-attempt and not third:** by attempt 3 the premise has usually laundered itself into the next variant and is no longer inspectable — the agent iterates on the *form* of the attempt, not on the *content* of the premise. The check has to fire while the premise is still visible.

**Coverage:** targets the generator directly. Catches 85.1 (Q2 surfaces "I am assuming Winston is right about `muteForFade`") at attempt 2, not attempt 6. Catches 85.6 (Q2 surfaces "I am assuming the runtime a11y-tree path is viable on iOS 26") at attempt 2, not attempt 6 — without depending on commits, so the in-session form is covered too.

### B (SPECIALIZATION) — Falsification-first for architect framings — `feedback_falsification_first_for_framings.md`

> When an architect framing names a specific mechanism as the cause, the next code action MUST be an observation that distinguishes "mechanism X is the cause" from "mechanism X is not." Not a patch.

**Role under the layering:** specializes Q2 for the case where the premise is "the cause is mechanism X." Falsification IS substantiation in that case. Keeps the rule strong for architect-named hypotheses, which are the highest-confidence form of laundered premise.

### C (DOWNSTREAM SAFETY NET) — Patch-count circuit breaker — `feedback_patch_count_circuit_breaker.md`

> After two follow-up "fix" commits chasing the same symptom, the third commit MUST be diagnostic, not another patch.

**Role under the layering:** redundant when rule A fires; fires when rule A didn't. Reaching this rule is itself a signal that the upstream self-check is not working — to be flagged when it triggers. Kept to catch the visible cross-commit form of the failure even if the in-session check was skipped.

### D (DOMAIN) — Audio listening-test gate — `feedback_verify_audio_features.md`

> Audio-path changes require a Michael listening test on Grand Piano + Sine Wave at `noteDuration=1s` before flipping spec to done. Tests-green is necessary but not sufficient.

**Role under the layering:** the domain instance of Q1 for audio — *what signal would have indicated progress?* For audio, the signal is audible, not test-green. Parallel to `feedback_verify_visual_features` for visual output.

## Residual gaps — explicitly named

1. **High review-patch density (85.8 form) suggests the implementation pass takes on too much at once in complex domains.** Different shape from the random-changes pattern: not "wrong premise iterated" but "too much done at once, review catches a lot." A complementary direction is "for audio / concurrency / data-model stories that touch more than N files, the implementation lands in two commits — a structural pass and a wiring pass — with adversarial review between them." Not adopted in this retro — flagged for discussion.

2. **The subtractive-first heuristic and cheap-research-first rule were considered and explicitly not adopted as memory entries.** They overlap meaningfully with the four adopted rules; in particular, the progress-check + substantiation rule's Q2 ("what would verify the premise?") will often surface "a 5-minute research probe" or "remove the redundant cleanup path and see if the symptom persists" as the natural next action. The retro records them as contributing factors only.

3. **Adopted measures are agent-level rules in memory; they do not change the BMad workflow itself.** A future iteration could mechanise the same checks at workflow-template level — e.g., a "post-merge bug-chase template" parallel to the story template that requires Q1/Q2 answers before the first patch. Out of scope for this retro.

(The earlier residual gap "in-session iteration without commits is not caught" was closed by adopting the progress-check + substantiation rule as the primary measure. The rule fires on attempts, not commits, so the 85.6-form is now covered.)
