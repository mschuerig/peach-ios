# Deferred Work

## From: Fix MIDI pitch bend lost on sound source change (2026-03-27)

- **Session leak on sound source change**: `onChange(of: soundSource)` replaces `pitchMatchingSession` and `pitchDiscriminationSession` without calling `stop()` on the old instances. If a session was active, its internal Tasks (MIDI listening, training loop) capture `self`, preventing deallocation. The old session's tasks run indefinitely until the AsyncStream finishes. Consider calling `stop()` before reassignment, or restructuring sessions to replace their NotePlayer rather than being fully recreated.
- **AsyncStream single-consumer**: `MIDIKitAdapter.events` is a single `AsyncStream` shared between `PitchMatchingSession` and `ContinuousRhythmMatchingSession`. While sessions are mutually exclusive by design, `AsyncStream` is documented as single-consumer. Consider using `AsyncBroadcastSequence` or per-session streams if multi-consumer support is ever needed.

## From: Fix AVAudioUnitSampler thread-unsafe reset crash (2026-04-25)

- **CC#123 doesn't reset pitch bend/controllers**: The old `auAudioUnit.reset()` reset all controller state including pitch bend. The replacement CC#123 (All Notes Off) only silences note-ons. If pitch bend was applied during playback and a new schedule starts, the bend could carry over. In practice this is mitigated because `sendPitchBend` is called explicitly before each `startNote`, but scheduled-only playback paths don't reset bend state.
- **`clearSchedule()` doesn't silence hanging notes**: When `clearSchedule()` is called, no All-Notes-Off is sent. Notes whose note-on was dispatched but note-off hasn't been reached will ring indefinitely. Pre-existing issue — the old `.reset()` was also only in `scheduleEvents()`, not `clearSchedule()`.

## From: Fix spectrogram sharing (2026-03-30)

- **Rhythm spectrogram export temp file cleanup**: `RhythmProfileCardView.renderShareImage()` writes PNGs to the temp directory on each re-render but doesn't track/delete previous renders, unlike `ChartImageRenderer.render()` which uses `lastRenderedURLs` for cleanup. Consider unifying both export paths through `ChartImageRenderer`.

## From: Story 80.0 Beat/Subdivision refactor review (2026-06-02)

- **Rename `currentGapPosition` → `gapPositionInCurrentBeat`** on `ContinuousRhythmMatchingSession`: with the new `currentBeatPosition` also being `BeatPosition?`, both observable properties are typed identically and only their names disambiguate "where the playback head is" vs. "where the gap is in the current beat". Surface area is one property + its tests + `ContinuousRhythmMatchingScreen`/`DotView` call sites. Low-risk pure rename; deferred only because the spec scope was already wide.
- **Concurrency audit of the sequencer @Observable + Task pattern**: `BeatProvider` is not `Sendable`, `SoundFontBeatSequencer.currentBeat` is mutated from a background `Task`, and `ContinuousRhythmMatchingSession.gapPositions` is written from the sequencer's polling Task. The shape predates 80.0 and the Swift 6.2 strict-concurrency build is clean, but the review (Blind hunter + Edge case hunter) flagged it as a latent data-race surface. Needs a focused audit (probably `/swift-concurrency-expert`) before any second discipline starts sharing a sequencer instance.
- **CRM refill state-reset on `samplePosition` wrap**: `ContinuousRhythmMatchingSession.lastEvaluatedCycleIndex` (and the new `lastPublishedCycleIndex`/`lastPublishedSubdivisionIndex`) are not reset when the sequencer refills its batch and resets `samplePosition` to 0. Unreachable in current play (refill happens at ~25 trials in; trials never span a refill boundary), but the latent state-mismatch means `cycleMissed` would stop firing if it ever did. Same shape pre-80.0; surfaced incidentally by Edge case hunter (finding #15).
- **Protocol-level contract tests for `SequencerEngine`**: no tests verify that `SoundFontEngine`'s `SequencerEngine` conformance matches the contract exercised by `MockSequencerEngine`. The two could silently diverge (e.g., what `clearSchedule()` does mid-render). Predates 80.0 — was true for `StepSequencerEngine` too.
- **Signed-offset bounds validation in `Beat.events`**: a `.note(offset: .milliseconds(-N))` on a beat's first subdivision can produce a negative `sampleOffset`, which the audio scheduler doesn't handle. No production user supplies negative offsets today, but Story 80.1 (TimingOffsetDetection on `BeatProvider`) will introduce signed offsets. Either add a bounds-check or precondition in `Beat.events`, or document that the caller is responsible for keeping offsets in-range. Decide as part of 80.1.
- **Deep-nesting safety in `Beat.events`**: `subdivisionDuration = beatDuration / Int64(subdivisions.count)` can truncate to 0 when subdivisions are many and beatDuration is small (or after several layers of recursion). The current code would then stack all notes at `baseOffset`. Not reachable from any production discipline; flag for the first nested-tuplet discipline.
- **`refillThreshold` uniform-tempo assumption**: `SoundFontBeatSequencer.refillThreshold` is computed from a single `samplesPerBeat` set once at start. Any future discipline that wants to vary tempo mid-session would mis-estimate refill timing.


## From: Story 80.1 Gapless looped playback review (2026-06-02)

- **One-tick litDotCount blip at batch refill** (`TimingOffsetDetectionSession.evaluatePlaybackPosition`): when `SoundFontBeatSequencer` refills (~every 500 beats), `engine.samplePosition` resets to 0. The session's `lastPublishedSubdivisionIndex` is high; modulo math may light a stale dot for one polling tick (8 ms) before resyncing. Sub-perceptual and self-correcting. Cheap fix: on observed negative jump in `globalSubdivisionIndex`, reset `lastPublishedSubdivisionIndex = -1` before the equality gate.
- **Sequencer cross-discipline serialization**: with TOD and CRM both calling `beatSequencer.start(tempo:beatProvider:)` on the shared singleton, the lifecycle coordinator must ensure the previous session has fully stopped (`await stopTask.value`-equivalent) before the next starts. Today the coordinator already serializes session activations, but no test pins this contract at the coordinator level. Adds confidence for any future third discipline. Overlaps with 80.0 D1 concurrency audit — consolidate when that runs.


## From: Story 80.2 Max-repetitions setting review (2026-06-02)

- **Stale `samplePosition` at new-trial start can fire cap immediately**: between `beatSequencer.start(tempo:beatProvider:)` returning and the render thread resetting `engine.currentSamplePosition` to 0, the polling task may sample a stale large value. With `maxRepetitions == 1` and an unlucky 8 ms tick at the boundary, `completedCycles` could already meet the cap before any audio is heard, immediately triggering `.repetitionCapReached` for the new trial. In practice the polling cadence is much slower than the render thread's reset, but the contract is implicit. Surfaced by Edge case hunter on 80.2; the same property of `BeatSequencer.timing.samplePosition` affects every consumer (TOD, CRM). Resolution candidates: (a) document the post-`start()` reset latency as a `BeatSequencer` contract guarantee with a test; (b) anchor TOD's `globalSubdivisionIndex` to a per-trial baseline `samplePosition` captured at start; (c) extend `BeatSequencer.timing` with a "trial-relative sample position" accessor. Coordinate with the 80.0 D1 concurrency audit and the 80.1 litDot-blip entry — same underlying surface.


## From: Story 81.2 TOD discrete-stops slider review (2026-06-03)

- **`AppTimingOffsetDetectionUserSettings.maxRepetitions` should clamp `> cap` as well as `< 1`**: the port currently clamps stored values `< 1` to `defaultMaxRepetitions` but lets arbitrarily large values (`Int.max`, a stale config from a future build, debugger writes) pass through unchanged. The new `DiscreteStopsSlider`'s `nearestStopIndex` computes `abs(stops[i] - value)` for each stop; with `value == Int.max` the arithmetic underflows and traps before any snap can happen. Theoretical (requires corrupt UserDefaults or manual seeding), but a real crash path with the storage-layer port as the natural fix site — clamping above the cap to `defaultMaxRepetitions` mirrors the existing below-floor clamp and removes the trap surface from every future caller. Surfaced by Edge case hunter on 81.2.


## From: Story 81.3 piano-keyboard for training note range review (2026-06-03)

- **O(N²) `PianoKeyboardLayout` x-position lookups**: `xPosition(forNote:)` is O(N) (filters `notes.prefix(while:)` for the white-key index), and `midiNote(at:)` calls it once per note (O(N²)). With 88 keys and ~60 Hz drag sampling this is ~465K ops/sec — well below the threshold of human-perceptible jank in Swift — but the data structure should be promoted to a precomputed `[MIDINote: CGFloat]` cache or an O(1) white-key-index table if a future caller renders a wider keyboard, animates per-key opacity at high frequency, or runs on a lower-performance device. Surfaced by Blind hunter on 81.3.
- **Voice Control "Tap C3" lost under the marker `.accessibilityRepresentation`**: spec Always rule line 30 wanted per-key `MIDINote.name` labels addressable by Voice Control ("Tap C3" works) alongside the two-marker adjustable representation for VoiceOver / Switch Control. `.accessibilityRepresentation` replaces the entire accessibility subtree, so Voice Control sees only the two Sliders. The two goals are mutually exclusive in a single SwiftUI configuration without a different mechanism (e.g., `.accessibilityCustomActions` plus markers as adjustable elements without `.accessibilityRepresentation`). 81.3 ships with VoiceOver/Switch Control fidelity; Voice Control falls back to the AX1+ summary-line + slider path. Future story: restructure the accessibility tree so per-key Voice Control addressing works on the non-AX1 path as well.
- **Auto-recenter scroll on bound change**: `NoteRangeSelector` scrolls to the midpoint between bounds only on first `.onAppear`. If the user drags a marker so far that it leaves the iPhone-portrait viewport, the marker stays off-screen. Cheap fix: add `.onChange(of: focusedMarker)` and `.onChange(of: lowerBound + upperBound)` to call `scroll.scrollTo(activeBound, anchor: .center)`.
- **Audio preview debouncing for keyboard `.repeat` phases**: holding ←/→ on macOS fires `onCommit` at the system key-repeat rate (~10 Hz). Each `playSoundPreview(note:duration: .milliseconds(400))` overlaps the previous. The sampler handles overlap gracefully but it's audibly muddy. Fix shape: serialize previews in `SettingsCoordinator` (cancel previous Task) or debounce at the call site.
- **AX1+ Slider partner-imposed range shifts during edit**: when the user moves one bound's Slider, the partner's legal range narrows synchronously. VoiceOver may announce the partner Slider's max changing under it. Standard behaviour for range-pair Sliders; acceptable for first cut but a UX polish item.
- **Black-key vs white-key y-aware hit-test**: `PianoKeyboardLayout.midiNote(at:)` is x-only. A tap on the bottom (white-only) half of a column over a black key resolves to the black key, even though visually the user pressed the white-key portion below it. Standard piano-UI behaviour requires y-coordinate awareness (top half: respect overlay; bottom half: white only).
- **`PianoKeyboardLayout` is main-actor-isolated; Core/Music style is `nonisolated`**: spec Change Log records the trap — `NoteRange.Hashable` is main-actor-isolated, so storing `NoteRange` in a `nonisolated` value fails to compile. The clean fix is to make `NoteRange` `nonisolated` (consistent with `MIDINote`) and then make `PianoKeyboardLayout` `nonisolated` too. Touches a widely-used domain type; deserves its own focused story rather than a Boy-Scout drive-by in 81.3.
- **`BoundMarker` tap target is ~30×30, below FR38's 44×44 minimum**: spec Change Log records the trade-off (44×44 markers would visually overlap at the 12-semitone minimum span on iPhone portrait). Multimodal access path (drag, tap-on-dimmed, kbd arrows, accessibility-representation Slider) means the drag target is one of several ways in, and AX1+ falls back to a system Slider entirely. Revisit if a user reports drag imprecision; the cleanest fix is to expand the marker pill itself (visual + tap target both grow) rather than decoupling content shape from visual shape.
- **`SettingsCoordinator.playSoundPreview` swallows audio errors with `try?`**: pre-existing pattern in the coordinator (the existing zero-arg variant has the same shape) but the silent-failure mode means a broken preview is indistinguishable from a working one with the wrong sound font. Add `os.Logger` warning on error consistently across both `playSoundPreview` overloads.


## From: Story 82.1 offset-note-position setting review (2026-06-03)

- **Bare `Int` for `offsetNotePosition` violates "Domain types everywhere"**: the new setting flows as `Int` through the protocol, the settings struct, `buildBeat`, and the `TimingDotView` parameter — the same anti-pattern `maxRepetitions: Int` exhibits. Project context (`docs/project-context.md`) is emphatic that domain values get a value type ("a constant like `36` is meaningless; `MIDINote(36)` communicates intent"). Story 82.2 ratified `offsetNotePosition` as the final identifier (no rename in 82.4), so the natural moment to introduce an `OffsetNotePosition` value type is 82.4's cleanup sweep or a successor refactor story. The value type would absorb `clamped(_:)`, the `validOffsetNotePositionRange`, and a `zeroBasedIndex` accessor that eliminates the two manual `- 1` translation sites. Surfaced by Quality reviewer on 82.1.
- **Help body strings hard-code "four 16th notes"**: `offsetNotePositionSettingsHelp` and the training-screen Goal text both embed the literal subdivision count. Today they happen to match `TimingOffsetDetectionSession.subdivisionsPerBeat = 4`. Story 82.6 ships variable-length patterns and these two strings will drift unless they're parameterised or recomputed. Cheap fix at 82.6 time; not worth solving in isolation.
- **Boy Scout opportunity in `GridToggleRow`**: that widget has zero explicit accessibility (no `accessibilityLabel`, no selection trait). My TOD picker added both. Lifting `GridToggleRow` to the same standard is a 4-line change that benefits the Continuous Rhythm Matching gap-positions picker. Explicitly deferred by user direction: "We will have to revise this anyway to handle more complicated rhythmic patterns" — i.e., 82.6 will refactor the whole picker abstraction.
